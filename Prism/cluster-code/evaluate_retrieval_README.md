# Retrieval Evaluation

This module evaluates graph-based and vision-based floorplan retrieval results after the RPLAN preprocessing and retrieval pipelines have been executed.

The evaluation is not based only on the vector similarity returned by the retrieval index. Instead, each retrieved floorplan is compared with its query floorplan using architectural information from the preprocessed `layout_json` and `graph_json` files.

## Expected Input

The script expects the preprocessed RPLAN data to contain:

```text
data/processed/rplan/
├── layouts_json/
└── graphs_json/
```

It also expects retrieval outputs generated by the retrieval pipeline:

```text
outputs/retrieval_gpu_full/
├── graph_pipeline/
│   └── <query_id>_top10.json
├── vision_pipeline/
│   └── <query_id>_top10.json
└── pipeline_comparison/
```

The names `graph_pipeline` and `vision_pipeline` are the default pipeline names. Different names can be passed with `--pipelines`.

## What the Evaluation Measures

For every query floorplan and every retrieved top-k result, the script computes several architectural similarity metrics.

### Room Type Similarity

The script compares the room-type histograms of the query and retrieved floorplans. This checks whether two layouts have a similar semantic composition, for example similar numbers of bedrooms, bathrooms, kitchens, balconies, and living rooms.

### Room Count Similarity

The script compares the total number of rooms in the query and retrieved layouts. This prevents a layout with a very different number of rooms from being considered highly similar only because it has a similar visual appearance.

### Area-by-Type Similarity

The script aggregates normalized room areas by room type and compares the resulting distributions. This captures whether the relative size of functional areas is similar.

### Adjacency Similarity

The graph edges are converted into semantic room-type adjacency pairs. For example, an edge between a `LivingRoom` and a `Kitchen` contributes to a semantic adjacency descriptor. This metric checks whether the query and retrieved layout have similar topological structure.

### Relation Similarity

The script compares the Graph2Plan spatial relation identifiers found in the graph edges. It also computes a directed relation-triplet similarity using `(source_room_type, relation_id, target_room_type)`.

### Grid-Type Similarity

Each room has a 5x5 grid location from preprocessing. The evaluation compares descriptors of the form `(room_type, grid_x, grid_y)`, which gives a simple measure of spatial distribution similarity.

### Constraint Satisfaction

The script derives simple constraints from the query layout and checks whether each retrieved layout satisfies them:

- same kitchen count;
- same bathroom count;
- bedroom count within ±1;
- total room count within ±1;
- living room coverage when the query has a living room.

The average of these constraints is reported as `constraint_score`. A result satisfies `hard_constraints_satisfied` only when all constraints are true.

### Architectural Score

The script also reports an aggregate `architectural_score`, which combines several metrics:

```text
0.25 room type count similarity
0.15 room count similarity
0.15 area-by-type similarity
0.20 adjacency similarity
0.10 relation-id similarity
0.10 grid-type similarity
0.05 constraint score
```

This score is used only for analysis and reporting. It is not a replacement for the retrieval model score.

## Output Structure

A typical run creates:

```text
outputs/evaluation_resnet50/
├── metrics_per_result.csv
├── metrics_by_query.csv
├── metrics_by_rank.csv
├── pipeline_summary.json
├── pipeline_summary.md
└── plots/
    ├── summary_bar.png
    └── rank_curve.png
```

### `metrics_per_result.csv`

One row for each query-result pair. This is the most detailed output.

### `metrics_by_query.csv`

Aggregated top-k metrics for each query and pipeline.

### `metrics_by_rank.csv`

Rank-wise metrics. This is useful to check whether architectural quality decreases as rank increases.

### `pipeline_summary.json`

Machine-readable summary of the evaluation.

### `pipeline_summary.md`

Standalone markdown report with the main evaluation results.

### `plots/`

Summary plots comparing the graph and vision pipelines.

## Dependencies

The evaluation script does not require CUDA, PyTorch, torchvision, or FAISS. It only reads JSON and CSV-like retrieval outputs.

Install the required packages with:

```bash
pip install numpy matplotlib
```

If the project environment already ran preprocessing and retrieval, these packages are usually already installed.

## Usage

Run from the project root, not from inside `cluster-code`.

### Windows PowerShell

```powershell
python .\cluster-code\evaluate_retrieval.py `
  --processed-root data\processed\rplan `
  --retrieval-root outputs\retrieval_gpu_full `
  --outputs-root outputs\evaluation_resnet50 `
  --top-k 10 `
  --clean
```

### Linux / Cluster

```bash
python cluster-code/evaluate_retrieval.py \
  --processed-root data/processed/rplan \
  --retrieval-root outputs/retrieval_gpu_full \
  --outputs-root outputs/evaluation_resnet50 \
  --top-k 10 \
  --clean
```

## Evaluating Specific Pipeline Folders

By default, the script evaluates:

```text
graph_pipeline
vision_pipeline
```

To evaluate only one pipeline:

```bash
python cluster-code/evaluate_retrieval.py \
  --processed-root data/processed/rplan \
  --retrieval-root outputs/retrieval_gpu_full \
  --outputs-root outputs/evaluation_graph_only \
  --pipelines graph_pipeline \
  --top-k 10 \
  --clean
```

To evaluate custom pipeline folders:

```bash
python cluster-code/evaluate_retrieval.py \
  --processed-root data/processed/rplan \
  --retrieval-root outputs/retrieval_experiments \
  --outputs-root outputs/evaluation_custom \
  --pipelines graph_pipeline vision_pipeline_dinov2 \
  --top-k 10 \
  --clean
```

## Recommended Workflow

1. Run preprocessing.
2. Run the graph and vision retrieval pipelines.
3. Visually inspect several retrieval grids.
4. Run this evaluation script.
5. Compare graph and vision pipelines using `pipeline_summary.md`, `metrics_by_query.csv`, and the plots.
6. Use the quantitative results to decide whether to test additional vision encoders such as DINOv2, ViT, or CLIP, or to move toward a learned GNN-based graph encoder.
